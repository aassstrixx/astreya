# Производительность: причины лагов и долгой загрузки, что сделано

Рабочий документ оптимизации (22.11.2026). Замеры — Chromium в песочнице **без GPU** (WebGL программный): по ним честно оцениваются байты, запросы, число и порядок загрузок; **реальная частота кадров на телефонах здесь не измеряется** — её надо смотреть на устройстве (см. «Как проверить на телефоне»).

## 1. Что выяснилось (главная, эмуляция телефона 390×844, без прокрутки)

| Что | Было | Причина |
|---|---|---|
| Загрузка при открытии | **295 запросов, 17,5 МБ** | движок зала (`js/jar.js`) сразу тянет **все 180 кадров** (60 цвет + 60 глубина + 60 спрайт баночки = 13,8 МБ), чтобы потом прокрутка не ждала; плюс 17 картинок журнала (1,7 МБ), которые на экране появляются лишь в конце |
| «Прогрев» анимации | лаги первые секунды, потом ровно | пока кадры качаются, декодируются и заливаются в видеопамять (`setLow`, `setKey` в `js/jar-gl.js`), это идёт в основном потоке параллельно с прокруткой; чем больше байтов — тем дольше «разгон» |
| Размер кадров | цвет 140–210 КБ на кадр (качество ≈ 92) | кадры закодированы с запасом; на экране телефона они всё равно разворачиваются до ширины холста (≈ 744 px) |
| Повторный заход / переход между страницами | всё грузится заново | у хостинга срок кэша 10 минут, версия в адресе (`?v=`) меняется только с выкладкой; своего кэша не было |
| CSS главной | 387 КБ, **используется 20 %** | на каждую страницу подключён общий набор, плюс `css/home-path.css` (21 КБ, «маршрут партнёра» прежней главной) — на новой главной-доме не используется совсем |
| Старые файлы в репозитории | ≈ 8 МБ неиспользуемых картинок, 4 папки `docs/_backup-*` | **на скорость не влияют**: браузер качает только то, на что есть ссылка. Мешает не «память старого сайта», а то, что стоит на пути загрузки (см. выше) |

Не причина: `data.js` (137 КБ, сжимается до ~35 КБ), шрифты (6 файлов, 190 КБ), число DOM-узлов (≈ 2000), сам JS (за первые 6 с в замере основной поток занят в основном заливкой текстур, а не скриптами).

## 2. Что сделано

1. **Картинки журнала по приближению** (`src/pages/home-house.js → deferImgs`, `js/house.js`): у `<img>` журнала вместо `src` — `data-src`; адрес подставляется, когда до читалки остаётся ≈ 0,4 экрана (читалка начинается через 2,6–3 экрана от верха, книга раскрывается в её глубине). Без JS те же картинки лежат в `<noscript>`. Итог: −60 запросов, −1,5 МБ при открытии.
2. **Кадры зала пережаты** (качество 82, размер кадра не менялся; `tools/perf/reencode-frames.py`): цветные наборы `m`, `d`, `ff`, `ffm` — 37,1 → 18,8 МБ (−49 %), PSNR к прежним кадрам: мин 39,1 дБ, средн 40–44 дБ; на сравнении фрагментов 1:1 различий не видно. Карты глубины (`z*`, без потерь) и спрайты баночки (`j*`, альфа) не тронуты. Загрузка главной на телефоне — **17,5 → 12,2 МБ**, кадры героя 13,8 → 9,6 МБ. Прежние кадры — в git (до коммита «Оптимизация…»).
3. **Кэш в браузере — service worker** (`src/sw-template.js` → `sw.js`, регистрация в `js/core.js`): файлы с `?v=` и шрифты — сначала кэш; страницы — сначала сеть (3,5 с), потом копия. Версия выкладки внутри `sw.js`: новая выкладка очищает старый кэш. Только https, не localhost, не автоматизация; `?sw=1` включает, `?sw=0` выключает и снимает. Замер (`tools/perf/sw-check.js`, телефон): первый заход 245 запросов / 11 МБ → перезагрузка 96 / 4,2 МБ (то, что при первом заходе ещё не успело загрузиться) → переход на каталог 25 / 1,5 МБ → **возврат на главную 1 запрос / 0 МБ**.
4. **CSS главной**: `home-path.css` не подключается к главной-дому (`src/layout.js`, остаётся только в запасном режиме `house.enabled = false`) — −22 КБ блокирующего CSS.
5. **Уборка**: удалены `docs/_backup-*` (4 папки прежних версий страниц), резервы `assets/company/_backup-atrium-v1-2026-11-16`, `atrium-v2*` (атриум v2 отменён владельцем). Всё есть в git-истории.

## 3. Что не сделано и почему

* **Прогрев упирается в основной поток**, а не только в сеть (на 30 Мбит/с в песочнице все кадры дошли за ≈ 6,5 с, на 9 Мбит/с — за ≈ 40 с при ожидаемых 9 с: поток занят заливкой текстур, сеть ждёт). Настоящая настройка бюджета заливки (`UP_GAP_*`, `UPQ_MAX`, `LOWDEC`, окно `RES`) требует замеров на телефоне — без них легко испортить плавность, которую владелец принял.
* **Регулятор нагрузки на телефонах выключен** (`GOV_PHONE = false` в `js/jar.js`): включение (холст 0,8 → 0,65 при затяжных медленных кадрах) нужно проверять на устройстве, иначе возможно возвращение «мыла» и зубчиков на кромках.
* **Деление `?v=` по группам файлов**: сейчас версия одна на всю выкладку — после любой выкладки кэш (в т. ч. кадры) сбрасывается целиком. Решение — хэш содержимого по группам (кадры, скрипты, стили); это отдельная переделка сборки.
* Откладывание неважных скриптов (`assistant-brain.js` 141 КБ, `guide.js`, `sales*.js`) до простоя: они инициализируются при загрузке; перенос требует правок каждого модуля.
* Прежняя главная (запасной режим `house.enabled = false`: `src/pages/home-x.js`, `home-path.js`, `css/home-path.css`, кадры `assets/jar-arch/{d,m,zd,zm,j,jm}` ≈ 22 МБ) оставлена как откат: в браузере посетителя она не участвует. Удаление возможно по слову владельца (метка отката `restore-before-astreya-house-2026-10` в git остаётся).

## 4. Инструменты замера (`tools/perf/`)

* `serve.js` — сервер HTTP/2 + gzip (https://localhost:8831) и обычный http://localhost:8832, счётчик запросов `/__count`, `/__reset`.
* `requests.js <mobile|desktop> <страница> [мс]` — сколько и чего загружается (по каталогам кадров, скриптам, стилям); `BASE=…`.
* `warmup.js <Мбит/с> <rtt мс>` — когда кадры дошли по сети и когда движок отметил их загруженными.
* `trace.js` — самые долгие события основного потока за первые секунды.
* `coverage.js` — какая доля CSS/JS страницы реально используется.
* `dead-css.py` — статический поиск CSS-правил без единой ссылки (на сайте сейчас ≈ 10 КБ из 712 КБ).
* `sw-check.js` — проверка кэша: первый заход, перезагрузка, переход, возврат.
* `reencode-frames.py` — пережатие цветных кадров с контролем PSNR.

## 5. Как проверить на телефоне

Открыть главную с `?diag=1` (вверху появится журнал: размер экрана, память устройства, режим, события регулятора), прокрутить зал сразу после загрузки и через 10–15 с; сравнить ощущения и прислать скриншот журнала. Если лаги остаются только в первые секунды — следующий шаг — настройка бюджета заливки по этим данным.
