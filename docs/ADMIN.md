# Админ-панель сайта «Астрея»

Админка нужна, чтобы **полностью управлять содержимым сайта без разработчика**: тексты на всех страницах, товары и витрина, новости и газета, мероприятия и обучение, контакты и реквизиты, бренды, меню, картинки. **Нельзя** (и не нужно) менять структуру сайта: порядок и набор блоков, вёрстку, анимации, CSS, а также фоновые изображения, сцены и рендеры — они показаны в библиотеке только для просмотра.

## Как это устроено

* Сайт статический (GitHub Pages). Страницы собирает `node tools/build.js` из `data/*.json` и шаблонов `src/pages/*.js`.
* Админка — отдельная программа без зависимостей: `server/` (Node.js 18+). Она правит `data/*.json`, **сама пересобирает сайт** после каждого сохранения, проверяет результат (`tools/check.js`) и **откатывает правку**, если сайт не собирается.
* GitHub Pages программы не запускает, поэтому админка работает **на компьютере или сервере заказчика** и кнопкой «Опубликовать» отправляет изменения в GitHub (`git push`). Подробности сервера — `server/README.md`.
* Тексты шаблонов (то, что раньше было зашито в `src/pages/*.js`) вынесены в реестр `src/texts-registry.js` + `src/texts/*.js`; шаблоны вызывают `T('страница.блок.ключ')`. Правки заказчика лежат в `data/texts.json` (ключ → текст). **Пока ключ не правили, на сайте исходный текст — страницы собираются байт в байт как раньше.**

## Запуск одной командой

В папке сайта (репозиторий с `data/`, `src/`, `server/`):

```bash
ADMIN_LOGIN=admin ADMIN_PASSWORD='ваш-пароль-не-короче-12-знаков' PUBLISH_GIT=1 node server/index.js
```

Откройте `http://localhost:8080/admin/`. Первый вход — пароль потребуют сменить. Остальное:

| Переменная | Зачем |
|---|---|
| `PORT` | порт (по умолчанию 8080) |
| `PUBLISH_GIT=1` | включает кнопку «Опубликовать» (нужны установленный `git` и право записи в репозиторий: ключ SSH или токен в адресе `origin`) |
| `PAGES_BRANCH` | (необязательно) ветка, из которой GitHub Pages собирает сайт: если она не совпадает с веткой репозитория на сервере, «Опубликовать» покажет предупреждение |
| `DATA_DIR` | где хранить заявки, пользователей, копии (по умолчанию `server/data`, не попадает в репозиторий) |
| `REQUIRE_2FA=0` | отключить обязательный второй фактор (по умолчанию он требуется администратору и редактору) |

Для постоянной работы на сервере — `server/Dockerfile`, `server/deploy/` (nginx, systemd) и `server/README.md`.

### Как опубликовать правки

1. Правьте нужные разделы — каждое сохранение пересобирает сайт; в «Предпросмотре» видно результат.
2. «Публикация → Опубликовать»: **шаг 1** — проверка сборки, **шаг 2** — список изменённых файлов и читаемый список правок («Было / Стало»), **шаг 3** — комментарий и кнопка. Админка делает `git add`, `commit` и `push`; GitHub Pages обновится через 1–2 минуты.
3. Что-то пошло не так — «История и откат»: у каждого раздела хранятся копии прежних версий (последние 60); можно посмотреть, что изменилось, и вернуть прежнюю версию, затем опубликовать ещё раз.

Публикация отправляет изменения в ту ветку, на которой стоит репозиторий сервера (она показана в «Опубликовать» полем «Ветка публикации»), — именно из неё GitHub Pages должен собирать сайт (GitHub: Settings → Pages → Branch). Если отправить не удалось (нет прав, ветка защищена, на GitHub есть более новые изменения, нет связи), админка объясняет причину и что делать; правки при этом сохраняются и закоммичены на сервере, а повторное нажатие «Опубликовать» отправляет их ещё раз.

Если `PUBLISH_GIT` не включён, админка покажет подсказку; готовый сайт можно скачать архивом («Публикация → Скачать сайт архивом», только администратор) и выложить на обычный хостинг.

Раздел «Оформление» (фоны страниц) убран из меню и оставлен как служебный (`#/design`, только администратор): по условию задачи фоны и структура не правятся заказчиком.

### Роли

* **Администратор** — всё.
* **Редактор** — всё содержимое, картинки, предпросмотр, публикация, история. Не видит: настройки, интеграции, пользователей, журнал, копии данных, персональные данные, заявки, запуск. Второй фактор обязателен, как у администратора (если не отключён `REQUIRE_2FA=0`).
* **Менеджер** — только заявки.

### Горячие клавиши и защита от потерь

`Ctrl+S` — сохранить открытый раздел или окно; `Ctrl+K` — быстрый переход и поиск по товарам, брендам, новостям, мероприятиям, страницам. Несохранённые правки: предупреждение при закрытии окна, переходе в другой раздел и закрытии вкладки; черновики форм и текстов сохраняются в браузере и предлагаются к восстановлению.

## Реестр текстов (для разработчика)

* Запись в `src/texts/<страница>.js`: `['ключ', 'Подпись для редактора', 'Исходный текст', {type, max, hint, optional}]`; ключ получается как `страница.блок.ключ`.
* Типы: `line` (одна строка), `text` (абзац), `rich` (можно `<br>`, `<em>`, `<strong>`, `&nbsp;`…), `link` (страница сайта, якорь, https, tel, mailto). Значения подставляются с `{имя}`-метками: `T('ключ', {pct: …})`.
* В шаблоне: `${T('contacts.hero.h1')}` (готовый HTML, экранируется), `Traw('…')` — сырой текст, если шаблон экранирует сам. В файлах, где имя `T` занято, импортируется как `TX`.
* **Проверка:** `node tools/check-texts.js` — каждый ключ реестра используется, каждый `T('…')` есть в реестре, правки заказчика проходят проверку. Сервер проверяет те же правила при сохранении (длина, пустое, `<`/`>`, ссылки).
* **Подписи для браузерных скриптов** (`js/*.js`): в скрипте стоит `AT('ui.блок.ключ', 'исходный текст')` (`AT` — короткое имя для `window.Astreya.T`); значения заказчика попадают в `js/data.js → texts`. У таких записей в реестре флаг `js: true`: в них запрещены `< > " ' \` и обратные кавычки (их вставляют в разметку), а `check-texts.js` сверяет, что текст в скрипте совпадает с исходным в реестре.
* **Метки `{имя}`** объявляются в записи как `ph: ['имя']`; сервер не примет метку, которой в поле нет (иначе страница показала бы «{ошибка}»).
* **Тексты из данных** (`data/content.json`, `data/redesign.json`) собирает `server/lib/datatexts.js`: любые русские строки этих файлов показываются в «Текстах страниц» (блоки «Данные: …») и пишутся обратно в свой файл с проверкой версии (409, если текст уже изменили) и пересборкой. Структуру (порядок, число пунктов) по-прежнему правит «Все данные сайта».
* Чтобы вынести новый текст: добавьте запись в реестр и замените строку в шаблоне на `T('ключ')`; пересоберите сайт и убедитесь, что `git diff` готовых страниц пуст (кроме хэша выкладки `?v=`).

## Демо-файл админки (один HTML)

`npm run admin:demo` (или `node tools/admin-demo.js путь/к/файлу.html`) собирает **один файл** (около 8 МБ), который открывается двойным щелчком из папки, без Node и без интернета: все разделы админки, настоящие данные из `data/*.json`, шрифты (Playfair Display, Manrope), упаковки товаров, фото преподавателей, логотипы.

* Формы работают: правка текстов (в т.ч. из данных), товаров, новостей, брендов, меню, картинок (загрузка, папки, переименование), история и откат с «что изменилось», поиск Ctrl+K. Всё живёт в открытой вкладке; после обновления страницы возвращаются исходные данные, сам сайт не меняется.
* Недоступно (честный ответ «В демо недоступно: …»): пересборка и проверка сайта, публикация на GitHub, заявки, копии данных, двухфакторный вход, проверка внешних сервисов, скачивание архива и CSV. Предпросмотр сайта в рамке показывает пояснение, ссылки «Посмотреть на сайте» открывают опубликованный сайт.
* Как устроено: генератор запускает настоящий сервер на пустых данных, снимает его ответы на все запросы админки (`/api/config`, `/api/texts/registry`, `/api/texts/data`, `/api/news/layout`, `/api/files/overview`, `/api/launch`, `/api/security`…) и встраивает их; изменяющие запросы обрабатывает `tools/admin-demo-backend.js` (тот же код сравнения версий и «текстов из данных», что на сервере). Порядок скриптов берётся из `server/admin/index.html`, поэтому новые разделы попадают в демо сами; если у раздела появился новый запрос, добавьте его в список `STATIC_GET` в `tools/admin-demo.js` (и, если он меняет данные, обработчик в backend).
* Файл не содержит адресов, путей и паролей компьютера, на котором собран (генератор проверяет это сам); в репозиторий его класть не нужно.

## Что осталось не вынесено в «Тексты страниц» и почему

Инвентаризация (`grep` по `js/*.js`, `src/**/*.js`, `tools/build.js`: русские строки вне `T()`/`AT()`). Все целые фразы, подписи, кнопки, aria/alt и SEO-шаблоны вынесены; осталось только следующее.

| Что | Где | Почему не вынесено |
|---|---|---|
| Формы слов при числе: «позиция / позиции / позиций», бренд, товар, линейка, семинар, город, продукт, категория, день, вопрос, материал | `S.plural(...)` в `src/pages/*.js`, `src/components.js`, `js/*.js` | форма зависит от числа; фразы вокруг счётчика вынесены, сами формы слов — грамматика, не контент |
| Названия месяцев и дней недели («января», «в понедельник», «сегодня / завтра») | `js/shared.js`, `js/sales-pages.js`, `src/pages/news.js` | календарные формы для дат, склоняются по правилам; в тексте страниц не меняются |
| Города (Москва, Санкт-Петербург…) в карточках, подвале, карте | `src/pages/contacts.js`, `company.js`, `partners.js`, `src/layout.js` | дублируют офисы из `data/site.json` — правятся в «Контакты и реквизиты» |
| Сгенерированные файлы `js/data.js`, `js/kb.js` | сборка из `data/*.json` | это копия данных; правятся исходные разделы (товары, бренды, новости…), а не копия |

## Ограничения

* Подписи скриптов и SEO-шаблоны меняются так же, как тексты шаблонов, но запрещают кавычки/угловые скобки (скрипты) и неизвестные метки `{…}`. Структуру блоков (порядок, число пунктов в списках) по-прежнему правит «Все данные сайта»; список того, что не вынесено, — в таблице выше.
* Картинки: загружаются PNG, JPG, WebP, GIF; SVG (логотипы) кладутся в репозиторий вручную. Сжатие в WebP делает браузер (внешних библиотек у сервера нет); если браузер не умеет WebP, файл загружается как есть.
* У нового бренда нет «ниши» на 3D-стене страницы «Бренды» (это рендер): бренд попадёт в каталог, на свою страницу, в «Партнёрам» и «О компании», а на странице «Бренды» — отдельным списком под стеной. Новый товар сразу попадает на витрину (спрайт упаковки выбирается по типу).
* Слот газеты можно оставить пустым — сайт соберётся, но на странице газеты будет пустое место; админка предупреждает.
* Публикация — `git push` в ветку, настроенную в репозитории; сервер не создаёт pull request и не разрешает конфликты (при расхождении с GitHub сделайте `git pull` вручную).
