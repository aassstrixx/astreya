# Арена: как выбирали движок плавности вступления с баночкой

Жалоба была такой: после версии с WebGL-интерполяцией (v40) картинка стала «лагать» на компьютере и на телефоне. Вместо того чтобы гадать, варианты
сравнили на одинаковых сценариях прокрутки по одним и тем же метрикам.

## Что есть

| Файл | Что делает |
|---|---|
| `engine.js` | параметризованный движок: отрисовка (2D / WebGL), способ декодирования (`<img>`, ImageBitmap окном / «по требованию», Blob), движение (экспонента / пружина), смешивание кадров (узкое / линейное / ближайший / по потоку) |
| `engine-lod.js` | движок с несколькими уровнями качества (LOD) и регулятором нагрузки — прототип того, что теперь в `js/jar.js` |
| `engine-worker.js` | тот же движок целиком в Worker (OffscreenCanvas) |
| `arena.html` | сценарии прокрутки и метрики; запускается из `run.js` |
| `run.js` | прогон участников: `node run.js [--only v36,v40] [--device desk,mob] [--throttle 1,4] [--scen wheel,…] [--flush] [--out results.json]` |
| `variants.js` | участники турнира |
| `summary.py`, `rank.py` | таблицы из `results*.json` |
| `real.js` | проверка **настоящей страницы** (любой версии сайта из папки): интервалы кадров, длинные задачи, остановка, а для текущего движка — ещё и «видимая» ошибка |
| `decode-bench.js`, `fmt-bench.js`, `decode-hint-test.js` | стоимость декодирования по формату/разрешению; помогает ли `img.decode()` (нет) |
| `data/` | сводка скорости движения (`motion_*.json`) и план кадров |
| `.cache/` | запечённые наборы кадров для арены (в git не попадает) |

## Методика

* Playwright + Chromium, замедление процессора через CDP (`Emulation.setCPUThrottlingRate`: ×1 и ×4 — «слабый телефон»).
* Сценарии: колесо мыши (16 щелчков, родное сглаживание), бросок пальцем с затуханием, медленное чтение (160 px/с), средняя скорость (1100 px/с),
  вперёд–стоп–назад–стоп, прыжки (ползунок / якорь).
* Цикл — по таймеру 60 Гц (не rAF), чтобы видеть, сколько времени движок реально занимает в основном потоке.
* Метрики: `fps`, доля кадров дольше 33 мс (`over33`), время работы движка за кадр (`js`), доля «устаревших» кадров (`stale`), **видимая ошибка** `vis`
  (на сколько пикселей кадра 1920 показанное положение отличается от положения прокрутки; двоение при смешивании кадров добавляется), **рывки** `jud`
  (отличие реального шага картинки от шага плейхеда), зависания (`frz`), задержка (`lag`), время остановки (`settle`), «щелчок» при остановке (`stopJerk`).
* В песочнице нет видеокарты, растеризация идёт на процессоре. Поэтому абсолютные fps ниже, чем у людей, а затраты на растеризацию завышены;
  сравнивать нужно участников между собой, а `--flush` (принудительная растеризация) показывает самый пессимистичный случай.

## Что выяснилось

1. **Лаги v40 — от основного потока.** Загрузка текстур в WebGL (`texImage2D`) и завершение `createImageBitmap` выполняются в основном потоке и при быстрой
   прокрутке забивают его (работа движка 3–67 мс за кадр, 13–33 % кадров «устаревшие» — декодер не успевает). Рисование `<img>` прямо в 2D-canvas почти
   ничего не стоит по JS.
2. **Стоимость кадра ∝ числу пикселей**, формат (WebP/JPEG/AVIF) почти не влияет. Полный кадр 1920×1080 при быстрой прокрутке даёт 30–50 fps,
   лёгкий 960×540 держит ~58–60.
3. **Плотность важнее гладкого смешивания.** Запечённые заранее промежуточные кадры (по потоку, офлайн, `tools/jar-render/bake_mid.py`) вдвое уменьшают
   «рывок» и видимую ошибку, не стоя ничего в браузере. Интерполяция потока в шейдере давала хорошее качество, но стоила слишком дорого по основному потоку.
4. **Уровни качества (LOD)** по скорости: полные кадры в покое и при медленной прокрутке, лёгкие запечённые при быстрой, совсем лёгкие — только по
   сигналу регулятора нагрузки (интервалы кадров дольше бюджета). На слабом процессоре регулятор снижает рывки и ошибку.
5. Пружина (критическое затухание) лучше простого сглаживания: нет рывка на старте и «щелчка» при остановке; ω≈20 даёт отставание ≈0,1 с и остановку за ≈0,3 с.
6. `img.decode()` как подсказка перед отрисовкой не помогает; `imageSmoothingQuality` 'low' и 'high' по стоимости близки.

Победитель — «три уровня + регулятор» (`g_on` в `variants.js`); он и реализован в `js/jar.js`.

## Отдельные цифры (песочница, компьютер 1280×720, ×1 / ×4 CPU)

| Участник | fps ×1 | кадров >33 мс ×1 | видимая ошибка (px) | рывки (px) | fps ×4 |
|---|---|---|---|---|---|
| v36: `<img>`, 180 кадров, экспонента | 59,6 | 2,3 % | 14,3 | 18,9 | 57,2 |
| `<img>`, 278 кадров, пружина ω=20 | 58,7 | 2,4 % | 6,4 | 9,5 | 57,6 |
| запечённые 555 кадров, линейное смешивание, ω=20 | 59,7 | 2,2 % | 3,3 | 0,0 | 53,4 |

(первые три строки — скрытый canvas, измеряется работа движка; последняя — с принудительной растеризацией, поэтому fps ×4 ниже.)

## Раунд 2: «пролаги» при скролле и чёткость (по видео и скриншоту пользователя)

**Щелчки колеса.** В браузерах без «плавной прокрутки» колесо даёт ступеньки по 100 px. На записи экрана (покадровый разбор: сопоставление шаблонов) страница
прыгала на 100 px за кадр с паузами по 10–12 кадров, а на границе сцены с баночкой — ещё и откатывалась назад на 70–80 px: сглаживание колеса
(`js/motion.js`) то включалось, то выключалось по зоне, и недокрученное старое значение тянуло страницу обратно. Что сделано и как выбрано:

* `scroll-sim.js` — численная арена на 60 Гц: щелчки колеса (раз в 35 / 70 / 140 мс и неровно) → сглаживание страницы → пружина плейхеда.
  Метрики: шероховатость шага (отклонение от скользящего среднего), задержка, остановка. Экспонента с постоянной .17 при каждом щелчке меняет скорость
  скачком (шероховатость страницы 11,7 %); пружина колеса ω=10 + пружина сцены ω=24 даёт 3,4 % страницы / ~1 % плейхеда при той же задержке ≈0,3 с и
  более быстрой остановке (≈0,8 с против 1,1 с). Сглаживание теперь везде одинаковое, без отключения в зоне сцены.
* Проверка на настоящей странице (реальные wheel-события, нативной плавности нет): было 41 «сырой» прыжок > 55 px и 95 пустых кадров, стало 4 и 6.

**Растянутая картинка на телефоне.** Холст пересчитывался только по событию `resize`; если сцена меняла размер без него (встроенные браузеры мессенджеров, поздно
пришедший CSS), картинка растягивалась (воспроизведено: искажение ×1,88 — как на скриншоте). Теперь `ResizeObserver` на сцене + `object-fit: cover` у холста.

**Чёткость.** `sharp-gen.py` / `sharp-run.js` / `sharp-eval.py`: один исходник без потерь → кандидаты (разрешение × качество WebP, а также AVIF) → отрисовка
в canvas браузером → SSIM / PSNR / «SSIM по деталям» (15 % самых контрастных пикселей: текст этикетки, кромки). Холст 1920 px: полные кадры q80 — 0,985 по деталям,
прежний лёгкий 960×540 q70 — 0,947, лёгкий 1280×720 q78 — 0,969; q80 → q90 у полных почти не видно (0,985 → 0,990 за +72 % веса). `imageSmoothingQuality='high'`
почти не повышает чёткость (доли дБ), зато на процессорной растеризации замедляет кадр в 10–20 раз — остался 'low'. AVIF даёт то же качество за вдвое меньший вес
(и декодируется не медленнее в Chromium), но скорость декодирования в Safari проверить нечем, а запасной набор удвоил бы репозиторий — отложено.
Решение: средний уровень 1280×720 (ПК) / 630×1120 (телефон), прежние лёгкие наборы остались запасным низким уровнем.

* Раунд 10 (ПК): средний 1120 / 1280 / 1440 против прежнего 960. 1280 по плавности не хуже прежнего (57,0 против 56,3 fps, кадров >33 мс 2,9 % против 3,8 %), 1440 заметно хуже.
* Раунд 11 (ПК): пороги переключения «полные ↔ средние» 18/9 → 5/2,5 кадра полного набора в секунду: рывки на медленной прокрутке 2,6 → 0,5 px, кадров >33 мс 2,2 → 0,5 %,
  fps при замедлении ×4 19,6 → 25,6. Низкий уровень «по скорости» (а не по регулятору) не помог.
* Раунд 12 (телефон, DPR 2): средний 540 / 630 / 675 / 720. 630: кадров >33 мс 4,7 % против 8,1 % у прежней версии, рывки 0,2 против 1,9 px; 675 — на уровне прежней, 720 — чуть хуже.

## Раунд 3: первое открытие сайта (холодный кэш, мобильная сеть) — `cold.js`

Жалоба: «при первом открытии анимация сильно лагает». Причина — не отрисовка, а загрузка: пока кадры не пришли, движок показывал ближайшие из уже загруженных,
и картинка шагала. `cold.js` открывает страницу с пустым кэшем через локальный HTTP/2-сервер (`h2-server.js`; как GitHub Pages, одноразовый сертификат с закреплённым
отпечатком), ограничивает сеть (wifi 40 мс / 5 МБ/с, 4g 100 мс / 1,5 МБ/с, slow4g 300 мс / 0,25 МБ/с; телефон — процессор ×4), ждёт заставку и сразу листает со
скоростью 600 px/с. Меряет ошибку показанного положения кадра, «двоение» (смешивание далёких кадров), сколько кадров каждого набора пришло.

Что нашлось в прежней загрузке (v42):
* 4 «полосы» (3 на телефоне): каждый запрос ≈ задержка + размер, при задержке 100–150 мс канал использовался на ~20 % — скорость упиралась в задержку, а не в полосу;
* полные кадры около положения грузились раньше средних, но показываются они только в покое; пока человек листал, средние (их и видно) голодали (16 % против 66 % полных);
* «каркас» среднего набора — каждый 8-й кадр — шагал на 60–120 px;
* загрузка начиналась только после события `load`.

Что сделано (проверено вариантами: число «полос» 8 / 14 / 24, глубина «каркаса», окно смешивания, а также крошечный набор «превью» 480×270 на весь сценарий — отвергнут:
он откладывал резкие кадры на 4g, выигрыш только на самой медленной сети): кадры берутся через `fetch` → Blob → `<img>` (не задерживает `load`, стартует сразу), 16 полос
на компьютере и 10 на телефоне, порядок «первый кадр → полные у положения → каркас → средние с окном впереди по ходу движения и от грубого к тонкому → полные в покое»,
пока движение идёт — полные не грузим, пока кадров рядом нет — смешиваем ближайшие загруженные (не дальше 8).

| | сеть | ошибка положения (px), было → стало | кадров с ошибкой > 20 px | средних кадров загружено к старту / +3 с |
|---|---|---|---|---|
| ПК | wifi | 4,7 → **0** | 10 % → 0 | 33 % / 46 % → **75 % / 100 %** |
| ПК | 4g | 14,3 → **0** | 33 % → 0 | 15 % / 18 % → **41 % / 82 %** |
| ПК | slow4g | 17,2 → **0** (двоение 24 px) | 33 % → 0 | 3 % / 8 % → 5 % / 14 % |
| Телефон | wifi | 8,1 → **0** | 18 % → 0 | 20 % / 24 % → **30 % / 59 %** |
| Телефон | 4g | 11,5 → **0** | 26 % → 0 | 10 % / 13 % → **25 % / 52 %** |
| Телефон | slow4g | **260** → **0** (двоение 16 px) | 50 % → 0 | 2 % / 6 % → 7 % / 18 % |

Событие `load` не задерживается (781 против 968 мс на 4g). На самой медленной сети (2 Мбит/с) резкие кадры приходят не сразу, и пока их мало, картинка слегка двоится при
быстрой прокрутке, но едет по положению (раньше — шагала на сотни px). Абсолютный fps в этой проверке ниже у новой версии (рисуется больше разных кадров, а не одни и те же
«устаревшие» — в песочнице всё растеризуется процессором).
